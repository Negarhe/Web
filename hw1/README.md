

# تمرین Git

## سؤال ۱ — `git merge` و `git rebase` (۳ نمره)

هر دو تغییرات یک شاخه را وارد شاخۀ دیگر می‌کنند، ولی شکل تاریخچه فرق می‌کند.

`git merge`**:** یک ادغام سه‌طرفه بین جد مشترک و نوک دو شاخه انجام می‌دهد و یک کامیت ادغام با دو والد می‌سازد (اگر `main` جلو نرفته باشد، فقط fast-forward می‌شود). کامیت‌های قبلی و هششان دست نمی‌خورند و تاریخچه غیرخطی می‌ماند.



```text
A---B---C---F---M   (main)
     \         /
      D-------E     (feature)
```



`git rebase`**:** کامیت‌های شاخه را برمی‌دارد و یکی‌یکی روی نوک `main` دوباره اعمال می‌کند. کامیت‌های جدید (`D'`، `E'`) هش تازه دارند، یعنی تاریخچه بازنویسی می‌شود و خطی است. تعارض ممکن است برای هر کامیت جدا حل شود.



```text
A---B---C---F           (main)
             \
              D'---E'   (feature)
```



**کاربرد** `merge`**:** ادغام یک قابلیت تمام‌شده در شاخۀ مشترک، مثلاً ادغام `feature-login` در `main` با pull request. چون شاخه عمومی است، نباید کامیت‌ها بازنویسی شوند و کامیت ادغام هم قابل `revert` است.

**کاربرد** `rebase`**:** به‌روز کردن شاخۀ خصوصی خودم با آخرین `main` پیش از pull request (`git fetch && git rebase origin/main`). شاخه فقط مال من است، پس بازنویسی آسیبی ندارد و تاریخچه تمیز و خطی می‌شود.

**قاعده:** کامیت‌هایی را که روی شاخۀ مشترک پوش شده‌اند `rebase` نکنید.

## سؤال ۲ — انتخاب بخشی از تغییرات (Hunk) (۳ نمره)

hunk یک تکۀ پیوسته از تغییرات در خروجی `git diff` است که با سرآیندی مثل `@@ -14,3 +14,4 @@` شروع می‌شود (محل و تعداد خط‌ها در نسخۀ قدیم و جدید).



```bash
git add -p README.md
git diff --staged
git commit -m "Clarify the setup steps"
```



گیت هر hunk را نشان می‌دهد و می‌پرسد: `y` یعنی stage کن، `n` یعنی نکن، `s` یعنی به تکه‌های کوچک‌تر بشکن، `e` یعنی دستی ویرایش کن، `q` یعنی خروج. با `git diff --staged` می‌بینم دقیقاً چه چیزی کامیت می‌شود. بعد از کامیت، hunk‌هایی که برایشان `n` زده‌ام در working tree می‌مانند و در `git diff` دیده می‌شوند تا در کامیت بعدی بروند.

**چرا مفید است:** اگر یک فایل چند تغییر بی‌ربط داشته باشد (رفع خطا، تغییر ظاهری، کد اشکال‌زدایی)، می‌توان هر کدام را در کامیت جدا گذاشت و کد موقت را بیرون نگه داشت. هر کامیت یک کار انجام می‌دهد و بازبینی، `revert` و `bisect` ساده‌تر می‌شود.

## سؤال ۳ — پیدا کردن منشأ خطا با `git bisect` (۳ نمره)

`git bisect` بین یک کامیت سالم و یک کامیت معیوب جست‌وجوی دودویی می‌کند. در هر گام کامیت وسط را checkout می‌کند، ما آن را `good` یا `bad` علامت می‌زنیم و بازه نصف می‌شود. برای N کامیت حدود log₂(N) آزمایش کافی است.



```bash
git bisect start
git bisect bad            # نسخۀ فعلی خراب است
git bisect good v1.8      # این نسخه سالم بود
# بعد از آزمایش هر کامیت:
git bisect good           # یا bad یا skip
git bisect reset          # پایان و برگشت به شاخه
```



**مثال:** تعداد کالاها در نسخۀ فعلی غلط است ولی در `v1.8` (حدود ۱۸۰ کامیت قبل) درست بود. بعد از حدود ۸ گام گیت اعلام می‌کند `c8d41ab is the first bad commit` و با `git show c8d41ab` خط‌های مقصر دیده می‌شوند. با `git bisect run ./test.sh` هم می‌توان کل کار را خودکار کرد؛ کد خروج ۰ یعنی `good`، ۱۲۵ یعنی `skip` و بقیۀ کدهای ۱ تا ۱۲۷ یعنی `bad`.

**چرا مفید است:** به‌جای بررسی صدها کامیت، با چند آزمایش و بدون حدس، دقیقاً کامیت مقصر (با diff، نویسنده و پیامش) پیدا می‌شود.

## سؤال ۴ — بررسی تغییرات پیش از کامیت (۳ نمره)

فرض: بخشی از تغییرات `README.md` stage شده (الف) و بعد فایل دوباره ویرایش شده. هر چه stage نشده، یعنی بقیۀ تغییرات دور اول به‌اضافۀ ویرایش دوم، را (ب) می‌نامم. `tmp/` هم untracked است.

### ۱. بررسی وضعیت

- `git status`: نمای کلی؛ `README.md` هم در staged و هم در unstaged دیده می‌شود و `tmp/` در Untracked.
- `git diff`: تغییرات unstaged (فقط ب).
- `git diff --staged`: تغییرات staged که وارد کامیت بعدی می‌شوند (فقط الف).

تغییر staged در index ثبت شده و کامیت می‌شود؛ تغییر unstaged فقط روی دیسک است تا وقتی `git add` شود.

### ۲. کامیت بدون `-a`

با `git commit -m "..."` فقط تغییر الف ثبت می‌شود، چون `git commit` محتوای index را ذخیره می‌کند و `git add` همان لحظه یک snapshot از فایل در index گذاشته است؛ ویرایش‌های بعدی خودبه‌خود وارد آن نمی‌شوند. تغییر ب به‌صورت unstaged باقی می‌ماند و `tmp/` هم چون untracked است وارد نمی‌شود.

### ۳. جلوگیری از اضافه شدن `tmp/`

خط `tmp/` را در `.gitignore` می‌گذارم. اما این فقط روی فایل‌های untracked اثر دارد؛ اگر فایلی از `tmp/` قبلاً کامیت شده باشد، باید آن را از index حذف کرد (فایل روی دیسک می‌ماند) و این حذف را کامیت کرد؛ از آن به بعد `.gitignore` جلوی اضافه شدن دوباره‌اش را می‌گیرد:



```bash
git rm -r --cached -- tmp/
git commit -m "Stop tracking tmp/"
```



## سؤال ۵ — رفع merge conflict در کار گروهی (۴ نمره)

من در `feature-description` و هم‌تیمی‌ام در `main` یک خط از `README.md` را متفاوت تغییر داده‌ایم و روی `main` با `git merge feature-description` تعارض پیش آمده.

### ۱. علت

در ادغام سه‌طرفه، یک خط در هر دو شاخه نسبت به جد مشترک به دو شکل متفاوت عوض شده و گیت نمی‌تواند تصمیم بگیرد کدام درست است. تغییر بخش‌های جدا از یک فایل تعارض نمی‌سازد؛ فقط تغییر خط‌های یکسان یا مجاور (یا حذف فایلی که طرف دیگر ویرایش کرده).

### ۲. پیدا کردن تعارض

`git status` فایل را زیر Unmerged paths نشان می‌دهد. داخل فایل:



```text
<<<<<<< HEAD
This project suggests courses based on student grades.
=======
This project suggests courses using enrollment history.
>>>>>>> feature-description
```



بین `<<<<<<< HEAD` و `=======` نسخۀ `main` است و بین `=======` و `>>>>>>>` نسخۀ شاخۀ ادغام‌شونده.

### ۳. حفظ هر دو تغییر

فایل را ویرایش می‌کنم، دو متن را ترکیب و همۀ نشانه‌ها را حذف می‌کنم:



```text
This project suggests courses based on student grades and enrollment history.
```

```bash
git diff --check
git add README.md
git commit
```



برای اطمینان از اینکه هیچ conflict marker نمانده، `git diff --check` را اجرا می‌کنم: هر نشانۀ باقی‌مانده را با شمارۀ خط گزارش می‌کند (`leftover conflict marker`) و خروجی خالی یعنی فایل تمیز است. چون فقط خط‌های تغییرکرده را بررسی می‌کند، با خط‌هایی مثل زیرخط `=======` عنوان‌های Markdown اشتباه نمی‌گیرد. بعد `git add` حل شدن تعارض را اعلام می‌کند و `git commit` کامیت ادغام را می‌سازد.

### ۴. لغو merge

`git merge --abort` همه‌چیز را به وضعیت پیش از `merge` برمی‌گرداند (تا وقتی کامیت ادغام ساخته نشده). چون working tree پیش از `merge` تمیز بود، این بازگشت کامل و بی‌خطر است.

## سؤال ۶ — انتخاب روش مناسب برای بازگرداندن تغییرات (۴ نمره)

### ۱. دور ریختن ویرایش stage‌نشده در `notes.txt`



```bash
git restore -- notes.txt
```



فقط working tree همین فایل به نسخۀ staging (که با آخرین کامیت یکی است) برمی‌گردد. staging، تاریخچه و فایل‌های دیگر دست نمی‌خورند. این ویرایش قابل بازیابی نیست.

### ۲. خارج کردن `notes.txt` از staging با حفظ ویرایش‌ها



```bash
git restore --staged -- notes.txt
```



فقط index به `HEAD` برمی‌گردد؛ ویرایش‌ها روی دیسک می‌مانند و به‌صورت unstaged دیده می‌شوند.

### ۳. خنثی کردن کامیت push‌شده روی `main`



```bash
git switch main
git pull
git revert --no-edit c0ffee1
git push origin main
```



اول `main` را به‌روز می‌کنم تا اگر هم‌تیمی‌ها بعد از من push کرده باشند، push من رد نشود. `git revert` یک کامیت جدید می‌سازد که اثر `c0ffee1` را معکوس می‌کند؛ کامیت‌های قبلی تغییر نمی‌کنند و فقط یک کامیت به تاریخچه اضافه می‌شود، پس `push` معمولی کافی است. working tree و staging هم با کامیت جدید یکی می‌شوند. چون `c0ffee1` کامیت ادغام نیست، گزینۀ `-m` (انتخاب والد) لازم نیست.

`git reset --hard` و `push --force` مناسب نیست، چون کامیتی را که هم‌تیمی‌ها دریافت کرده‌اند از تاریخچه حذف می‌کند، تاریخچۀ آن‌ها را ناسازگار می‌کند و ممکن است کار دیگران را روی شاخۀ دور پاک کند.
